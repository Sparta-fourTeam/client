# 서버 전투 계약

`HttpBattleSessionApi`는 서버의 발급·결과 제출·포기를 담당한다. `HttpApiClient`와 인증 토큰 저장소를 전달해 사용한다. end가 보상·진척을 변경해도 응답은 비어 있으므로 `IBattleApi.SubmitResult`를 구현하거나 런타임 `LocalBattleApi`를 교체하지 않는다. 서버와 Local의 재화 변경을 한 전투에서 혼합하지 않는다.

## 요청과 응답

기준은 서버 PR #59(dev `e42def63a609ecaa68097e7c0bd449321e7d5788`)와 [배포 OpenAPI](https://doodle-defense.duckdns.org/api/v3/api-docs)다. 사용자 ID는 모든 경로에서 Bearer 토큰으로 결정한다.

| 경로 | 본문 | 성공 |
| --- | --- | --- |
| `POST /api/battle/start` | `{ "createId": "클라이언트 UUID" }` | `{ "battleId": "서버 발급 ID" }` |
| `POST /api/battle/end` | `{ "battleId": "서버 발급 ID", "stageId": 1, "clearedWave": 10, "rating": 2 }` | 200, 본문 없음 |
| `POST /api/battle/cancel` | `{ "battleId": "서버 발급 ID" }` | 200, 본문 없음 |

end에는 `BattleEndRequest`를 사용한다. 네 필드는 모두 필수이며 `clearedWave`는 0~20, `rating`은 0~3이다. DTO 생성 시 빈 battleId와 범위 밖 결과를 거절한다. `stageId`는 서버 카탈로그의 정수 ID이며 명세에는 최소값 제약이 없다. Local 테이블의 스테이지와 일치하는지 확인 없이 임의 변환하지 않는다.

start에는 `userId`, `stageId`, 데이터 개정, seed를 보내지 않는다. 서버는 새 키면 에너지 5를 소모하고 기존 세션을 덮어쓴다. 현재 세션과 키가 같으면 기존 battleId를 반환한다. cancel은 세션 삭제만 하며 환불 계약은 없다. end/cancel의 ID 불일치는 400, 세션 미존재는 404다.

PR #59의 end는 트랜잭션 안에서 세션을 먼저 삭제해 선점한 후 기본 경험치·골드·아이템을 지급하고 최고 클리어 등급을 갱신한다. 세션 삭제 실패 요청은 보상을 지급하지 않는다. 실패 시 롤백·동시성의 실제 DB 보장은 클라이언트 fixture 테스트로 입증하지 않는다. 성공 본문에 보상 내역·지갑·진행도 스냅샷은 없으므로 이를 만들어 반환하거나 Local 보상을 지급하지 않는다.

## 재시도와 불확실한 결과

입장 동작 하나에 `new BattleStartRequest()`를 한 번 만들고 성공 여부가 불확실하면 **같은 객체**로 `StartBattle(request)`를 재호출한다. 새 객체는 새 키이므로 이전 발급이 성공했다면 에너지가 다시 차감될 수 있다. 요청 객체의 `createId`는 읽기 전용 UUID이며 시작 메서드 내부에서 매번 생성하지 않는다. 401 토큰 재발급은 기존 HTTP 클라이언트가 같은 직렬화 본문으로 한 번만 재전송한다.

일반 네트워크 오류·시간 초과·5xx는 자동 재전송하지 않는다. start 성공 응답에 battleId가 없으면 `INVALID_RESPONSE`로 거절하며, 서버가 발급했을 가능성이 있으므로 같은 요청 객체를 유지한다.

end 응답이 유실되면 보상·진척이 이미 적용됐을 수 있다. 같은 요청을 다시 보낸 뒤 404를 받아도 이미 완료했는지 원래 없었는지 구분할 수 없으므로 성공으로 바꾸지 않는다. cancel도 동일하게 404를 성공으로 간주하지 않는다. 호출자가 오류를 숨기거나 로컬 보상을 대신 지급해서는 안 된다. 실제 연결 전 사용자 스냅샷 재조회·중복 지급 방지·결과 복구 정책이 필요하다.

이 모듈은 요청을 디스크에 저장하지 않는다. 앱 종료 후 복구·계정 전환 시 요청 수명·동시 입장 방지는 Player 그룹 연결 시 정해야 한다. 끝난 세션의 키는 서버에서 지워지므로 영구 멱등성은 아니다. start의 중복 키 조회와 에너지 락 획득은 별도이므로 동일 키 동시 요청의 DB 기반 검증도 필요하다.

## Player 그룹 연결 전 남은 정합성

- PR #59는 `GET /api/stage`, `POST /api/user/stage-progress/claim`을 추가했다. 별 보상 수령 응답은 stageId·clearRating·claimedRating이며 전체 지갑·아이템 상태가 아니다. `user/me` 스냅샷 재조회와 Player 그룹 6개 API의 상태 일관성을 함께 확인해야 한다.
- end의 stageId·clearedWave·rating은 클라이언트가 보내며 시작 세션에 스테이지·판정 근거가 묶이지 않는다. 서버 검증을 보장한다고 해석하지 않는다. 클라이언트 등급 계산과 서버 지급 결과·표시를 맞춰야 하며, 보상 계산을 Local 공식으로 복제하지 않는다. PR #59의 20웨이브 계산은 finalCoin/finalAmount 값 자체와 다를 수 있어 카탈로그의 의미도 확인해야 한다. 이를 클라이언트에서 임의 보정하지 않고 현재 서버의 지급 계약으로 취급한다.
- PR #58의 강화 구매는 `{ upgradeId, createId }`를 받고 `{ upgradeId, level }`만 반환한다. 전체 스냅샷은 별도 조회이며 서버는 unlockLevel을 검사하지 않는다.
- 서버 오류 본문은 status·error·message·path이며 기계 판독용 도메인 코드가 없다. 409는 에너지 부족과 락 충돌 모두 가능하므로 `HTTP_409`를 유지하고 message 문자열로 구분하지 않는다.
- 서버 Clock은 Asia/Seoul이고 에너지 시각은 offset 없는 LocalDateTime이다. 클라이언트 UTC 해석·Energy 테이블의 최대값/회복주기/입장 비용, 실제 DB 시각을 확인해야 한다.
- 도감 보상·에너지 회복·상점/퀘스트/튜토리얼 변경 API, 튜토리얼 ID 대응 및 전체 테이블 본문 전환은 여전히 남아 있다. 아이템 문자열 ID·gem/jem 호환 수정만으로 전체 Player 전환이 완료되지는 않는다.

OpenAPI 변경은 명세 배포의 증거이며 실제 보상 트랜잭션이나 DB 마이그레이션 완료의 증거는 아니다. 운영 상태 변경 요청 없이 계약만 확인하며, 실제 계정·동시성 검증은 로컬/테스트 DB에서 수행해야 한다.


## 전투 종료 뒤 서버 상태 조정

`HttpBattleResultReconciler`는 로그인 세대와 불변 `BattleEndRequest` 하나에 묶인 수명 짧은 조정기다. 최초 `Submit()`은 end를 한 번 보내고 `GET /api/user/me`를 이어서 읽는다. 같은 인스턴스의 `Submit()` 재호출과 `RefreshState()`는 GET만 한다. HTTP 클라이언트의 401 재발급에 따른 1회 재전송은 기존 인증 계약대로 유지된다. 생성 시 전달한 토큰 저장소를 end·조회·재발급 모두에 사용한다.

| end 관측 결과 | SubmissionStatus | 후속 처리 |
| --- | --- | --- |
| 2xx 응답 수신 | Acknowledged | 서버 상태 조회. 조회 실패가 나도 제출 확인은 유지하고 GET만 재시도 |
| 응답 유실·5xx·404·전송 중 취소 | Unknown | GET으로 현재 상태를 읽어도 이 전투의 완료로 승격하지 않음 |
| 그 외 확정 거절 응답 | Rejected | 관측 상태와 거절 코드를 분리. GET 성공을 제출 성공으로 바꾸지 않음 |

`BattleReconciliationResult.ObservedState`는 서버가 나중에 노출한 `ServerUserData`이며 해당 전투의 보상 내역·원자적 버전·처리 영수증이 아니다. 잔액이나 등급의 전후 차이로 보상을 추정하지 않는다. 날짜 자동 변환을 끄고 원문 날짜 문자열을 보존하며 필수 필드, 행 형태, 음수 재화·수량, 중복 ID, 수령 등급의 정합성을 검사한다. 부분 응답을 0이나 빈 목록으로 채워 반환하지 않는다.

같은 인스턴스의 동시 호출은 거절한다. 로그인·로그아웃으로 토큰 세대가 바뀌면 실제 전송 직전과 응답 반환 전에 차단한다. 이전 계정의 늦은 응답을 새 계정 상태로 반환하지 않으며, 세대가 유지되는 정상 refresh는 허용한다. 전송 전에 취소하면 제출 이력을 만들지 않지만, 전송 중 취소는 Unknown으로 남긴다.

조정기는 Local API·LocalSaveStore·PlayerProfile을 호출하지 않는다. 현재 `IBattleApi`/`StageManager`는 확정 보상 응답과 결과 재제출 멱등성을 요구하므로 이 조정기를 그 자리에 등록하지 않는다. RootLifetimeScope와 ServerConfig는 변경하지 않으며 실제 게임의 진행 저장은 계속 기존 Local 경로다.

### 확정 복구·실제 게임 연결에 필요한 계약

- **battleId별 영속 결과 조회/재제출 영수증:** 적용 여부, 확정 등급·보상 내역, 같은 결과 요청의 동일 영수증을 돌려줘야 한다. 현재 삭제된 세션의 404로는 완료와 미존재를 구분하지 못한다. 클라이언트에서 새 조정기를 만들거나 앱을 재시작하면 인스턴스 내 POST 제한도 사라지므로 이를 영구 멱등성으로 취급하지 않는다.
- **서버 상태 revision 또는 영수증과 일치하는 스냅샷:** user/me는 다른 구매·보상을 포함할 수 있어 특정 전투의 보상 차액을 증명하지 못한다. 현재 ObservedState를 전체 클라이언트 PlayerSnapshot으로 직접 적용하지 않는다. 퀘스트·상점 등 서버가 노출하지 않는 상태와 숫자 튜토리얼 ID도 Local 값으로 보충하지 않는다.
- **지속 복구와 제품 결정:** 재시작을 지원하려면 계정 식별자에 묶인 미확정 요청 저장과 서버 조회가 필요하다. 끝내 확정되지 않는 결과의 대기·재조회·이탈 UI 및 체크포인트 수명도 정해야 한다. 현재 조정기는 디스크 원장을 만들거나 결과 UI의 완료 판정을 바꾸지 않는다.
- 전역 Player 전환에는 입장 stageId/결과 검증, 등급·보상 표시, 에너지 시간대와 비용, 강화·별보상·도감·퀘스트·상점의 서버 일관성 및 서버 DB 검증이 여전히 필요하다. 조정기 fixture 테스트는 운영 처리나 실제 DB 동시성을 입증하지 않는다.

## 서버 영구 강화 테스트 모드

일반 모드의 기본 API 선택은 유지한다. Editor의 `Tools > Project Nova > Server Upgrade Test Mode`를 켜고 Boot부터 다시 재생하면 해당 Root 수명 동안 서버 조회·영구 강화 단건 구매만 사용하는 별도 모드가 된다. 개발 빌드에서는 `PlayerPrefs`의 `dev.server_upgrade_test` 문자열 `1`로 선택할 수 있다. 릴리스 빌드에서는 이 설정을 무시한다. 모드 변경은 실행 중에 적용하지 않는다.

이 모드는 서버 인증 후 Local 로그인을 생략하고, Local 표시 정보나 기존 저장·체크포인트를 읽거나 초기화하지 않는다. `ServerUpgradeTestBackend`가 `IPlayerApi`·`IUpgradeApi`를 함께 맡는다. 전투 시작/종료, 에너지 회복, 별·도감·퀘스트 보상, 상점 변경, 튜토리얼 완료, 계정 연결/삭제/닉네임 변경은 `SERVER_TEST_DISABLED`로 거절한다. 체크포인트 Load는 빈 결과이고 Clear/Flush는 파일에 접근하지 않는다. 전투·가이드 튜토리얼 자동 진입도 생략한다. 기존 Local 진행을 서버로 이전하거나 두 상태를 섞지 않는다.

단건 구매는 `{upgradeId, createId}`를 한 번 만들고 `POST /api/user/upgrades`의 `{upgradeId, level}` 확인 뒤 `GET /api/user/me`를 읽는다. 후속 조회의 강화 레벨이 확인된 결과보다 낮으면 완료하지 않는다. 응답 유실·5xx·409·잘못된 성공 응답은 미확정 요청으로 남고, 확인 버튼은 동일 키를 재전송한다. 구매 확인 후 조회만 실패했다면 GET만 재시도한다. 미확정 요청이 있는 동안 다른 키·다른 강화와 일괄 구매는 막으며 팝업을 닫아도 같은 Root의 요청은 남는다. 잔액 변화로 구매 성공을 추정하지 않는다.

새 구매 전 인증된 `GET /api/upgrade`로 선택한 강화의 최대 레벨·해금 레벨·재료 ID·다음 레벨 비용을 번들 견적과 비교한다. 차이가 있으면 POST를 보내지 않는다. 서버 값을 번들 테이블에 덮어쓰거나 표시 비용만큼 Local 재화를 차감하지 않는다. 이 비교는 구매와 원자적인 서버 견적 계약이 아니므로 다른 기기·관리자 변경까지 잠그지는 못한다. 전투는 차단돼 있으며 로비 효과 미리보기는 기존 번들 효과를 사용한다.

미확정 구매는 **메모리에만** 보존한다. 앱 종료·Root 재생성·계정 재인증 뒤의 동일 요청 복구를 보장하지 않는다. 서버에는 안정적인 계정 ID·상태 revision·구매 상태 조회가 없고, 409의 도메인 코드도 없다. 이 제한을 전역 런타임 전환이나 운영 지급 검증 완료로 해석하지 않는다. 서버가 제공하지 않는 퀘스트·상점·문자열 튜토리얼은 이 모드에서 사용할 수 없으며 Local 값으로 보충하지 않는다. 신규 계정 재화·해금은 서버가 제공한 그대로라 구매할 수 없는 계정도 있다.
